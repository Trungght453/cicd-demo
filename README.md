# cicd-demo

A NestJS service with one endpoint, written to be the subject of a CI/CD
demonstration. It is deliberately small: the interesting part is the pipeline
that will be built around it, not the application.

## The endpoints

```
GET /health  ->  200  application/json
GET /hello   ->  200  application/json
```

```json
{ "status": "ok", "version": "1.4.0", "commit": "a3f9c21" }
{ "message": "Hello from cicd-demo" }
```

Nothing else is routed. `GET /` returns 404, and there is a test that keeps it
that way.

## Contract or copy

The two endpoints are protected differently, on purpose.

`status` is a **contract**. A machine reads it and decides something from it, so
it is pinned to the exact string `ok`. Changing it to anything else turns the
pipeline red, because every caller that checks for `ok` would silently start
treating the service as unhealthy. That is a breaking change and it should cost
a conversation.

The greeting in `/hello` is **copy**. A person reads it, nothing branches on it.
Its tests assert that the response is 200, is JSON, and carries a non-empty
`message` string — and say nothing about the wording. Rewriting the sentence is
free. Deleting the field, or returning something that is not a string, is not.

Tests that pin copy are the reason people learn to ignore a red build. Test the
shape a caller depends on, not the words a human will want to change.

## Why those three fields

`status` answers whether the process is alive. It is computed from nothing: no
database, no disk, no call to another service. A health check that asks another
system reports that system's health, not its own, and turns one slow dependency
into a fleet-wide restart.

`version` and `commit` answer a different question: **which build is this?**
They are not read from `package.json`. They come from the environment, and the
pipeline is what sets them:

| Variable      | Set by                                      | Shown when unset |
| ------------- | ------------------------------------------- | ---------------- |
| `APP_VERSION` | the build step                              | `dev`            |
| `GIT_SHA`     | the build step, from the commit being built | `local`          |

That is the point worth demonstrating. After a deploy you call `/health` and
read the SHA back. If it matches the commit you merged, the deploy is proven
from the outside. If it does not, the pipeline reported success and shipped
something else — which is the failure that log-watching never catches.

Seeing `dev` / `local` in a deployed environment means the build step did not
stamp the artifact.

## Running it

```bash
npm install
npm run build
npm run start:prod
```

```bash
curl -s localhost:3000/health
# {"status":"ok","version":"dev","commit":"local"}

APP_VERSION=1.4.0 GIT_SHA=$(git rev-parse --short HEAD) npm run start:prod
curl -s localhost:3000/health
# {"status":"ok","version":"1.4.0","commit":"<your sha>"}
```

`PORT` overrides the default of 3000.

## Checks

These four are what a pipeline would run. All of them pass on a clean checkout.

```bash
npm run lint      # oxlint, type-aware
npm run build     # nest build, tsc under the hood
npm test          # vitest, unit
npm run test:e2e  # vitest, over real HTTP
```

Three layers of test, on purpose:

- `src/app.service.spec.ts` — the environment matrix, no framework involved
- `src/app.controller.spec.ts` — wiring only, against a stubbed service
- `test/app.e2e-spec.ts` — status code, content type, and that `/` stays 404

## Toolchain

NestJS 12 on Node, ESM (`"type": "module"`, so relative imports carry `.js`).
Generated by the Nest CLI, whose current defaults are **vitest** rather than
jest and **oxlint** rather than eslint. Worth knowing before writing the
pipeline: the commands are `vitest run` and `oxlint`, and older NestJS CI
examples found online will reference the wrong ones.
